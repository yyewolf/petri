# Simulating Node failures

Code that manages workloads, or that sets PodDisruptionBudgets, has to cope
with Nodes going away. On a [dedicated plane with Nodes](../guides/nodes.mdx),
a test can cause each failure itself, in the order it chooses.

## What you can cause

| Failure | How |
|---|---|
| The kubelet stops reporting | `node.SetReady(t, false)`: the Node turns NotReady, gets the `not-ready` taint, and its Pods freeze. |
| An administrator drains the Node | `node.Drain(t)`: cordon, then evict through the Eviction API, honouring budgets. |
| A Pod is evicted | `cp.Evict(t, pod)`, refused while a budget forbids it. |
| The Node disappears | `node.Delete(t)`: its Pods are force-deleted, as the Pod garbage collector does. |
| A Pod's process exits | `cp.FailPod(t, pod, exitCode)` or `cp.CompletePod(t, pod)`. |
| A Pod stops being ready | `cp.SetPodReady(t, pod, false)`. |

## What petri leaves to you

petri runs no node lifecycle controller. A NotReady Node is never tainted
`NoExecute`, and its Pods are never evicted by themselves. If a test needs
that, it evicts or deletes the Pods, or deletes the Node, when it chooses.
Because nothing happens on a timer, failure tests are deterministic.
