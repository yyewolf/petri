# Waiting

Controllers act asynchronously, so tests wait for results. petri's waits watch
the API server and return as soon as the result is there. You do not need
sleeps or polling loops.

## Waiting for one object

`petri.WaitFor(t, client, name, condition)` follows one object until the
condition holds. It fails the test after 30 seconds. The client is any typed
client-go resource client, such as `cs.AppsV1().Deployments(ns)`.

<CodeBlock language="go" title="deleted_test.go">{Deleted}</CodeBlock>

The wait lists the object, then watches from its resourceVersion, so it does
not miss a change made just before the wait started. If the watch expires, the
wait opens a new one. On timeout, the failure message shows the last state the
wait saw.

A condition is a `func(O) (bool, error)`. It receives `nil` while the object
does not exist. If it returns an error, the wait stops with that error. petri
provides these conditions:

| Condition | Holds when |
|---|---|
| `petri.Exists[O]()` | the object exists |
| `petri.Deleted[O]()` | the object does not exist |
| `petri.StatusCondition[O](type, status)` | `status.conditions[type]` has that status, for any object whose conditions have string `type` and `status` fields |

[`petri.WithTimeout(d)`](https://pkg.go.dev/github.com/yyewolf/petri#WithTimeout) changes the 30-second default. An earlier context deadline still
wins.

Custom resources usually have no typed client. Wrap a dynamic
`ResourceInterface` with `petri.DynamicResource` instead; the [CRDs](crds.mdx)
guide shows how.

## Waiting for anything else

## Without a testing.T

[`petri.WaitUntil(ctx, client, name, condition)`](https://pkg.go.dev/github.com/yyewolf/petri#WaitUntil) and
[`petri.RetryUntil(ctx, condition)`](https://pkg.go.dev/github.com/yyewolf/petri#RetryUntil) return an error instead of failing a
test. `WaitUntil` also returns the last object it saw. See
[Ginkgo and other frameworks](frameworks.mdx).
