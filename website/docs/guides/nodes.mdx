# Nodes and scheduling

petri simulates Nodes the way [kwok](https://kwok.sigs.k8s.io/) does. No
container runs. A Pod placed on a Node becomes `Running` and `Ready` at once,
with an IP from the Node's PodCIDR, and a deleted Pod goes away at once. The
workload controllers then behave as they do on a cluster.

A Node can run any test's Pods, so only
[dedicated planes](control-planes.mdx#dedicated-control-planes) have Nodes. The
shared plane refuses every Node operation. The samples on this page share a
helper that starts a dedicated plane:

<CodeBlock language="go" title="plane_test.go">{Plane}</CodeBlock>

## Adding Nodes

`cp.AddNode(t, petri.NodeOptions{...})` creates a Ready Node and deletes it
when the test ends. All options are optional:

| Option | Default |
|---|---|
| `Name` | `petri-node-` and a random suffix; set it when the test needs to know the name |
| `Labels`, `Annotations` | yours, plus the well-known `kubernetes.io/hostname`, `kubernetes.io/os` (`linux`) and `kubernetes.io/arch` (`amd64`) labels |
| `Taints` | none |
| `Capacity` | 32 CPUs, 256Gi of memory, 1Ti of ephemeral storage, 110 Pods |
| `Unschedulable` | `false`; `true` creates the Node cordoned |

Each Node gets its own PodCIDR and InternalIP. It reports a kubelet version and
conditions, as a real kubelet would.

## kube-scheduler

Enable `petri.SchedulerController` to run upstream kube-scheduler with its
default profile. It places Pods by requests, taints and tolerations, node
selectors, affinities and topology spread:

<CodeBlock language="go" title="scheduler_test.go">{Scheduler}</CodeBlock>

Without the scheduler, Pods stay Pending until the test places them. A plane
uses either the scheduler or manual placement; see
[manual placement and Pod expectations](pod-expectations.mdx).

## Changing Nodes

`AddNode` returns a `*petri.Node`. Its methods change the Node the way an
administrator or a failing kubelet would:

| Method | Effect |
|---|---|
| `Taint`, `Untaint` | Add or remove taints. |
| `Cordon`, `Uncordon` | Mark the Node unschedulable, or not. |
| `Drain` | Cordon, then evict every Pod but DaemonSet Pods through the Eviction API, retrying while a PodDisruptionBudget refuses. |
| `SetReady` | Report the Node Ready or not, with the matching `not-ready` taint. |
| `Delete` | Delete the Node and force-delete the Pods bound to it, as the Pod garbage collector does on a cluster. |

## Node failures

A Node that is not Ready behaves as if its kubelet were frozen. Pods bound to
it stay Pending and Pods deleted from it stay `Terminating` until it is Ready
again.

<CodeBlock language="go" title="notready_test.go">{NotReady}</CodeBlock>

petri runs no node lifecycle controller, so nothing reacts to a NotReady Node
by itself. There is no taint-based eviction and no `tolerationSeconds`. The
test decides what happens next, for example with `Drain` or `Delete`.

## What is not simulated

No container runs, so there are no probes, images, volumes, resource usage or
restarts, and readiness gates are ignored. A Pod stays `Running` until the
test finishes it with `CompletePod` or `FailPod`, or deletes it. Nodes send no
heartbeats and have no Leases.
