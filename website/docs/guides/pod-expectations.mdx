# Manual placement and Pod expectations

Without kube-scheduler, a Pod stays Pending until the test places it. The test
can use that moment as an assertion, the way a mock checks a call: it states
which Pods your code should create, and decides where each one runs.

The samples run on a [dedicated plane with Nodes](nodes.mdx).

## One Pod at a time

`cp.ExpectPod(t, matchers...)` waits for a matching Pod that is Pending and
unscheduled, and returns it. It never returns the same Pod twice.
`cp.Bind(t, pod, node)` places the Pod with the same `pods/binding` call
kube-scheduler makes.

## Declaring expectations

`cp.ExpectPods(t, matchers...)` registers an expectation. It claims matching
Pods as they are created, before anything else sees them:

<CodeBlock language="go" title="expectations_test.go">{Expectations}</CodeBlock>

| Method | Meaning |
|---|---|
| `Times(n)` | Claim `n` Pods; the default is one. Later matching Pods are left unclaimed. |
| `AnyTimes()` | Any number, zero included. |
| `BindTo(node)` | Bind each claimed Pod to `node`. |
| `Do(func(ctx, pod) error)` | Run your own action on each claimed Pod. |
| `Wait(t)` | Wait until the expected number of Pods were claimed and acted on. |
| `Pods()` | The Pods claimed so far. |

When the test ends, petri checks every expectation. One that claimed fewer
Pods than expected fails the test. An expectation never claims more than its
count, so extra Pods go unnoticed unless you call `cp.StrictPods(t)`, which
fails the test for each Pod no expectation claimed.

Expectations claim Pods in the order they were registered, and before
`ExpectPod` does. A Pod goes to the first expectation that matches it.

## Matchers

| Matcher | Matches Pods |
|---|---|
| `petri.InNamespace(ns)` | in a namespace |
| `petri.Labeled(key, value)` | with a label |
| `petri.OwnedBy(obj)` | owned by an object, by UID |
| `petri.PodMatching(description, func(*corev1.Pod) bool)` | for anything else; the description shows in failure messages |

A Pod must match every matcher given.

## Finishing Pods

No container runs, so the test decides how a Pod ends. This is how a Job
completes:

<CodeBlock language="go" title="job_test.go">{Job}</CodeBlock>

- `cp.CompletePod(t, pod)` marks the Pod `Succeeded`, with its containers
  terminated with exit code 0.
- `cp.FailPod(t, pod, exitCode)` marks it `Failed`.
- `cp.SetPodReady(t, pod, ready)` changes its readiness, to test how your code
  handles a Pod that stops being ready.
- `cp.Evict(t, pod)` evicts it through the Eviction API, so
  PodDisruptionBudgets apply.

The simulated kubelet never overrides what the test set.

## Scheduler or by hand

A plane places Pods in one way only. `Bind`, `ExpectPod` and `ExpectPods` fail
the test on a plane running `SchedulerController`. Enabling the scheduler on a
plane where the test placed Pods or registered expectations fails too. The
shared plane has no Nodes, so it refuses all of these.
